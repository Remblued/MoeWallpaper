# 国内可直连图源调研

**目标**：在**没有代理**的网络下能出图的图源。这是目前最大的可用性缺口——
三个内置图源全部在海外，国内直连一个都不通。

本文只记录**实测过**的东西。查来的说法一律标注来源，没跑过的不写进结论。

## 0. 判定标准

一个候选要同时满足五条才值得接：

1. **国内直连可通** —— 不开代理就能拿到响应
2. **免费、无需 API key** —— 要注册/申请的不算
3. **返回列表** —— 本项目的图源格式只吃"一次给一批"，不是单图
4. **内容合适** —— 二次元/动漫优先，且没有明显越界内容
5. **能承担长期维护** —— 有文档或长期存活的证据，不是个人随手搭的转发

第 3 条是最卡人的：国内免费接口**绝大多数是"随机单图"**（一次 302 到一张图），
而本项目一次要一页。

## 2. 360 壁纸：唯一可用的列表源

**分类接口**（用来证明这站还活着、以及确认分类 id）：

```text
http://cdn.apc.360.cn/index.php?c=WallPaper&a=getAllCategoriesV2&from=360chrome
→ 200, 18 个分类，其中 id=26 动漫卡通、id=36 4K专区
```

**列表接口**：

```text
http://wallpaper.apc.360.cn/index.php
    ?c=WallPaper&a=getAppsByCategory&from=360chrome
    &cid=26&start=0&count=20
→ 200, application/json, 24,077 B, 20 条, total="10000"
```

一条数据的实际形状（节选，删掉了广告位和空字段）：

```json
{
  "id": "2054206",
  "class_id": "26",
  "resolution": "2560x1440",
  "url":       "http://p3.qhimg.com/bdr/__85/t01e2fa62f505895db7.jpg",
  "url_thumb": "http://p3.qhimg.com/bdr/__85/t01e2fa62f505895db7.jpg",
  "utag": "动感手游 拔剑 眼神 原神",
  "create_time": "2022-01-18 19:55:05"
}
```

已经验证的三件事：

- **分页是偏移量**：`start` 是 0/20/40…，不是页码。
- **图片可走 https**：同一个 URL 把 `http://` 换成 `https://`，返回 200、
  `image/jpeg`、字节数完全一致（309,650 B）。这一点很关键，见 §4。
- **接口本身只有 http**：`wallpaper.apc.360.cn` 没有 TLS（2018 年的分析文章就提到
  "唯一不足就是不支持 SSL"，今天实测仍是这样）。

来源：端点参数来自
[腾讯云社区的文章](https://cloud.tencent.com.cn/developer/article/1145601)（2018 年），
**状态和字段是本次实测确认的**，不是照抄文章。

## 3. 为什么 Bing 不接

`https://cn.bing.com/HPImageArchive.aspx?format=js&idx=0&n=8` 确实返回 JSON 列表，
国内直连可达，但：

- 一页只有 8 张，且是**每日一张**的归档，不是可无限翻的图库
- 返回的是**相对路径**（`/th?id=...`），本项目格式要求绝对 URL
- 内容是**摄影照片**（沙丘鹤、国家公园），不是二次元——和这个应用的定位不符
- 用途受 Bing 服务条款约束，README 里"图源是公开 API"的说法会变得站不住

## 4. 落地需要改代码，不是改 JSON

360 这个源**不能只写一段 JSON 就接上**，缺三样东西：

1. **`{offset}` 占位符**。现在只有 `{page}`，而 360 要的是 `start=(page-1)*limit`。
   （这条早就挂在 `HANDOVER.md` 的债表里，估过"约 3 行"。）
2. **从 `resolution` 里拆宽高**。它的宽高是 `"2560x1440"` 一个字符串，而我们的映射
   要的是两个数字路径。要么加一个 `resolution` 字段由代码拆，要么这个源的
   `width`/`height` 留空（但那样分辨率筛选对它失效，而它明明有数据）。
3. **图片 URL 的 http→https 升级**。接口只给 http，而 WebView2 不会把 http 图片
   加载进一个安全上下文里。要么加一个 `httpsUpgrade` 开关，要么后端下载后本地供给。

第 3 条还有个更彻底的解法：**详情页和缩略图都改走后端下载 + 本地缓存**，前端只拿本地
路径。那样 http/https、防盗链、referer 这些事一次性全消失，还顺带有了缓存。工作量大
一些，但它解决的问题不止国内源。

## 5. 风险，写清楚再决定

- **这是非公开 API**。没有文档、没有 SLA、随时可能改或关。它从至少 2018 年活到
  今天（本次实测仍返回 20 条），但我们不能承诺它一直活着。**图源是数据**，所以死了
  就是改一段 JSON——这正是当初把图源做成配置的价值。
- **条款不明**。360 壁纸的图来自用户上传，版权归属不清。本项目不托管图片、只做
  链接和本地缓存，立场和接 wallhaven 时一致，但这一点要在 README 里如实写。
- **没有内容分级字段**。不像 wallhaven 有 `purity`、lolicon 有 `r18`，360 只有分类。
  我们只能固定 `cid=26 动漫卡通`，**无法像另外两个源那样用参数保证安全内容**。
  这违反 `model.rs` 里"安全参数必须是被消费的配置"那条原则，必须写进文档让人知道。
- **`total=10000` 可能是上限**，深翻页可能返回重复或空。

## 6. 结论与下一步

**已完成（v0.1.1）**：三处能力都补上了，360 排在 `sources/builtin/sources.json` 的第一位，
所以**打开应用默认就是国内源，不需要代理**。

新增的图源配置能力：

- `{offset}` 占位符：`start=(page-1)*limit`，配置里不用做算术
- `resolution` 字段：把 `"2560x1440"` 拆成宽高；同时配了 `width`/`height` 时以那两个为准
- `filter.httpsUpgrade`：把图片地址的 `http://` 换成 `https://`，否则 WebView 不会加载
- `filter.randomOffsetMax`：把 `{offset}` 换成**随机起点**。360 的列表是固定顺序，
  第 1 页永远是那 20 张；配 `8000` 后每次从 `[0,8000)` 里随机取 20 的倍数，
  "翻页"就变成了"换一批"，效果对齐 wallhaven 的 `sorting=random`

落地时配的测试：

- `start` 随页码正确递增（不是等于页码）
- `"2560x1440"` 能被拆成 2560 / 1080
- http 图片地址被升级成 https

**不接"随机单图 API"生态**：它们大多是个人转发，本次实测四个里死了三个，而且一次
一页要打 20 次请求，既不礼貌也不可靠。要支持它们得再引入一种图源类型，收益不抵成本。

如果哪天 360 也挂了，退路是 §4 提到的"后端下载 + 本地缓存"——那条路不依赖任何
接口形态，只依赖"能下载一张图"。

## 7. 第二批候选（2026-10-31 实测）

用户从搜索结果里挑了一批，逐个跑过：

| 候选 | 实测 | 判定 |
| --- | --- | --- |
| 接口盒子 `cn.apihz.cn/api/img/apihzimg{baidu,sougou,bz}.php` | 三个都 200，但 body 是 `{"code":400,"msg":"id参数不能为空…"}` | ❌ 全要 `id`+`key`；且"随机壁纸"自己标注非商用、版权来源不明 |
| `api.xyttkx.cn/ecy.php` | TLS 握手失败：`SEC_E_CERT_EXPIRED (0x80090328)` | ❌ 证书过期，`reqwest` 会直接报错 |
| `i.mukyu.ru`（雪涼 Pixiv） | `/random` → 200 `image/jpeg` **20,237,289 B** 单图；`/wtf` 是 HTML 瀑布流；`/docs` 是参数文档 | ❌ 没有列表接口，且单张 20 MB |
| `uapis.cn` | 有正经 OpenAPI（112 个路径）；`/api/v1/random/image` 是 **302 到单张图**，`/api/v1/image/bing-daily` 同理 | ❌ 单图，不是列表 |
| `api.yujn.cn` | `anime.php` → 404；站点根路径 15 s 超时（期间已收 1.75 MB） | ❓ 端点没给准，未验证 |
| **夜轻 `api.yppp.net`** | `/pc?return=all` → 200 `text/plain` **16,171 B / 440 行**；`/pe?return=all` → 200 **36,003 B / 976 行** | ⚠️ 形态可用，但卡在两个前提上，见 §7.1 |

### 7.1 夜轻是这批里唯一成体系的，但有三个硬伤

好的部分，都是实测：

- 440 张横图 / 976 张竖图，全是 `https://cdn.yppp.net/acg/{pc,pe}/N.webp`，顺序编号 1..N。
  20 张一页 = 22 页 / 48 页，**是真分页，不是每次重排**。
- 图片直取可用：`pc/1.webp` → 200 `image/webp` 374,722 B（2560×1446），
  `pc/220.webp` 2,891,972 B，`pc/440.webp` 5,414,714 B。
- 快：目录 0.32 s，单张 0.54–1.18 s。
- `?return=json` 返单张 + `width`/`height`，且是**字符串**形式——`number_at()` 已经能吃。
- 限流的表现是 **404**（Go 的 `404 page not found`，不是 429）。间隔 4 s 实测
  `return=all` 8/8、`return=json` 4/4 全成功；**背靠背请求就 404**。
  文档写的是"10 秒内超过 20 次 → 30 秒限流"。

三个硬伤：

1. **返回的是纯文本行，不是 JSON**。现有格式只吃 JSON + dot-path，`itemsPath` 没有
   "按行切"的形态。要接得新增一种 `lines` 形态；又因为接口本身不支持分页，
   还得把整份目录取回来**在本地切片**再按页返回。
2. **全是 webp**。`wallpaper/set.rs` 是直接把路径交给 `SystemParametersInfoW`，不做解码。
   本机能解 webp，是因为装了商店扩展 `Microsoft.WebpImageExtension 1.2.31.0`；
   **干净 Windows 上默认没有**。所以"设为壁纸"在多数用户机器上很可能会失败。
   这一点**没有实测**（实测就得改用户桌面），不能当成"应该没问题"。
3. **没有缩略图，CDN 也不给缩图**。`?imageMogr2/thumbnail/400x`、`?imageMogr2/format/jpg`、
   `?x-oss-process=image/resize,w_400` 三种都返回 `image/webp` 且**字节数与原图完全一致**，
   说明不认；`1.jpg` / `1.png` 全是 404。一页 20 张，最坏要拉 ~100 MB。

### 7.2 要接它得付的代价

| 缺的能力 | 改哪里 | 量级 |
| --- | --- | --- |
| `lines` 响应形态 + 本地切片分页 | `model.rs` / `loader.rs` / `fetch.rs` / `extract.rs` | 约 100–150 行 + 测试 |
| webp → jpeg（否则"设为壁纸"不可靠） | 新增解码依赖 + `current.rs::publish` 转码 | TBD（安装包会变大，**未实测，不许填估值**） |

## 8. 结论

三个海外源要靠代理；国内能直连、又"一次给一批"的，到今天仍然只有 360 一家。
夜轻是第二个**形态合格**的，但它把成本从"改 JSON"抬到了"改代码 + 加依赖"。

判定标准没变：**连"能不能拿来当壁纸"都不确定的，不该现在接。**
夜轻的图能看、能下载、能分页，唯独最核心的那个动作（设为壁纸）取决于用户装没装
商店里的 webp 扩展——这不是我们可以赌的。

- [ ] `api.yujn.cn` 的准确端点（目前只测到 404 与超时）
- [ ] 要不要为 webp 引入解码依赖——这是产品决策：拿体积换格式兼容
- [ ] 如果两个前提都做了，夜轻值得排在国内源第二位（`pc` 在后，`pe` 可选）
